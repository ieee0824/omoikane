# Gate 5: native target and release acceptance

Issue: [#545](https://github.com/ieee0824/omoikane/issues/545), parent
[#514](https://github.com/ieee0824/omoikane/issues/514).

The Gate 5 workflow builds actual distribution archives and executes their
contents on the matching native host. Full-suite tests and package builds run
in separate jobs, with one resolved Cargo.lock shared by all six jobs.
The same reusable workflow is a dependency of `release.yml`; publication cannot
proceed if any target, package smoke, or compatibility check fails.

Pull requests execute the gate through `release.yml` itself, so its three-target
build path is exercised before merge. The standalone native-JIT workflow also
runs on PRs; the release workflow calls that matrix again only for tag pushes
and manual preflights. Manual runs validate the complete release path without
publishing. Publication requires a `v*` tag push and successful prerequisites.
The reusable gate also runs directly after pushes to main.

| Distribution target | Native runner | Library | JIT backend |
| --- | --- | --- | --- |
| x86_64-unknown-linux-gnu | ubuntu-24.04 | libomoikane.so | System V x86-64 |
| aarch64-unknown-linux-gnu | ubuntu-24.04-arm | libomoikane.so | AAPCS64 |
| aarch64-apple-darwin | macos-15 | libomoikane.dylib | Apple arm64 / macOS code-memory policy |

This table identifies the tested support matrix; the matching revision's
`jit-gate5-report/gate.json` records its actual pass/fail decision. A green
cross-build alone, a stale report or a skipped native workload is insufficient.

macOS support is ARM64 only. On 2026-09-10 the project owner removed macOS
x86_64 from the supported distribution targets in #545. It is excluded from
release packaging and required native/full-suite CI. Historical Intel macOS
measurements describe earlier experiments, not current support guarantees.

## Archive and compatibility checks

The supported targets retain their archive names, C header and default library.
The default library is built without optional features and copied to staging
before building the separate `omoikane-jit-smoke` diagnostic executable with
`baseline-jit`. A `build.json` manifest records revision, compiler, target,
dependency-lock hash, file sizes and SHA-256 digests.

Each archive is extracted into a fresh directory. Its file digests must match
the manifest. A new process loads the extracted C library and exercises
JavaScript arithmetic plus DOM insertion/query identity through the public C
ABI. The extracted diagnostic executable uses `JsRuntime` with JIT explicitly
selected and compares execution with the interpreter. Neither operation relies
on running a build-tree executable as a substitute for the packaged file.

The full suite includes ignored tests and enables `baseline-jit,jit-differential`
on every target. Separate artifacts retain the native policy/seeded execution
report, Acid3 faithful/direct scores, pinned WPT results and Web API regressions.
Acid3, WPT and Web API probes retain the browser's default runtime policy, matching
the shipped default library. Native contract tests and the packaged diagnostic
explicitly select JIT execution and require native-entry evidence.
Acid3 must match the [pinned Selectors 4 expectation](../../tests/fixtures/acid3/selectors4-expectation.json)
in both modes: raw 99/100, completed index 100, and exactly the obsolete test 35
assertion. The original fixture and raw failure log are retained; another failure,
a missing log, or a synthetic 100-point score is rejected. WPT/Web API regressions must be zero.
The existing separately profiled ten-minute Gate 4 stress check remains required
on PRs; the native corpus in this workflow does not replace that check.

## Performance evidence and review

The packaged probe uses the existing arithmetic and monomorphic-property shapes
with four fixed seeds. Each shape/seed has five fresh-runtime samples per mode,
alternating JIT off/on ordering. Timing covers `eval` after declaration and
warmup, including the small call expression's parsing and host boundary. Runtime
construction and warmup are excluded from execution timing. Independent Rust
calculations supply expected checksums; JIT-on samples must record native entries
and property workloads must record native guard hits.

Compilation time and generated bytes cover the measured function's declaration
and warmup, separately from its warmed execution. Reports also contain measured
entry/bailout counts, guard misses and categorized deoptimizations. Source seeds
and generated-code snapshots accompany every target's results. The aggregate
reports median execution/compilation times, emitted bytes and bailout rates.
Raw per-seed samples remain available, so differing iteration counts are not
hidden by the aggregate.

`JsRuntime` retains its wall-clock deadline during the probe. The native loop
therefore returns for a deadline poll after at most 4096 iterations, then resumes
generated execution. These intentional interrupt deoptimizations count as
bailouts. The aggregate separates interrupt and non-interrupt bailout rates and
records property guard misses; a high total bailout fraction alone does not mean
property speculation failed. Do not disable the deadline to improve the numbers.

Review the architecture/OS results at the same source and dependency revision.
Investigate large code-size or compilation differences and any unexpected
bailouts using the retained counters and dumps. Runner hardware and operating
systems differ, so timing equality is not a gate and cross-host ratios are not
an isolated estimate of architecture quality. Record observed differences,
their explanation and the final support decision in #545 with the exact CI run
and artifact links. A successful execution aggregate supplies evidence for this
review; it does not itself demonstrate a speedup on every workload.

explicit no-go decision is recorded. Gate 5 support does not enable production
JIT, select a new default engine, remove Boa, or pre-approve Gate 6. The decision

## Reproduce one native target

Use Rust 1.98.1 and Python 3.11 or newer (CI uses Python 3.12). Run from a clean checkout; preserve the generated
lockfile between steps. Replace `TARGET` with the current rustc host triple.

```sh
python3 scripts/jit-gate5.py prepare .artifacts/jit-gate5/inputs
python3 scripts/jit-gate5.py suite TARGET .artifacts/jit-gate5
python3 scripts/jit-gate5.py package TARGET .artifacts/jit-gate5
```

Local results for one target cannot satisfy the three-target aggregate. CI retains
`jit-gate5-TARGET-suite`, `jit-gate5-TARGET-package`, the three verified archives,
the shared identity/lockfile and `jit-gate5-report`. Complete logs are uploaded on
failure as well; failed steps do not produce a passing target result.

The existing ignored local layout investigation also requires
`tests/output/blog-content.html` outside CI. Supply the investigation's existing
snapshot when running locally; a missing snapshot is a failed local run, not a
compatibility result. The test's existing CI behavior is unchanged.


### Suite job partitions (#1692)

Each supported target runs `suite-core`, `suite-wpt`, and `package` as separate
90-minute jobs. Core retains the original full-suite command and first seven
serialized sensitive commands. WPT retains the eighth serialized command, with
its original selector, features and test-thread setting. Their ordered union is
the original nine Rust commands; no test or evaluation limit is relaxed. The
local `suite` command remains available for a monolithic execution.

Both suite jobs fetch the pinned WPT checkout as runner setup. Core supplies
native, Acid3 and Web API reports; the WPT job supplies the final complete WPT
report. Logs, capacity snapshots and diagnostics use distinct part directories.
Both jobs may restore the shared suite caches; only a successful core job on main
may save Rust/Boa caches, avoiding competing writers and additional full caches.

CI aggregation explicitly requires split evidence, identical clean source/lock
and toolchain identities, exact command coverage, and successful actual matrix
jobs. A missing part, conflicting monolithic report, altered command or cancelled
job produces no-go even when other reports say passed. Historical timings explain
the split but do not guarantee cold-run completion. Capacity (#1681) and elapsed
time (#1692) remain separate acceptance conditions.

Before execution, core lists the unfiltered full test universe; WPT lists its
exact selected test in its own harness. Reports retain harness-qualified test
names from these listings and from every executed command. Aggregation requires
the combined execution multiset to equal the core inventory, each test once,
with the sole WPT test exclusively in the WPT part. Counts alone cannot satisfy
this check. Missing names, overlapping substring skips and duplicates fail.
Listing compiles but does not run tests; WPT lists only its own integration target
so it does not compile unrelated integration binaries for inventory collection.

Each part fetches WPT independently and records its explicit report paths, WPT
configuration, Cargo target/jobs, temporary directory and test environment in
`suite-environment.json`. System font installation remains runner setup. WPT does
not consume core reports or core server state. Results include the workflow run
ID and attempt; different latest attempts from the same run can compose, while
cross-run evidence is rejected. The actual matrix result must also be success.
Cold/warm timings, cache usage and successful x86 Boa-cache saves remain required
observations when CI runs; fixture success alone does not establish them.
